# Развитие спутникового мониторинга (Тульская область)

Дорожная карта по четырём направлениям, построенная **поверх существующей
инфраструктуры**, а не с нуля.

## Что уже построено (фундамент)

- **`DistrictNdviSeries`** — предагрегированный ряд NDVI по `район × дата × угодье`.
- **Детектор фенологии** `agrocosmos/services/yield_features.py` — SOS / peak / EOS / iNDVI.
- **ML-пайплайн прогноза урожайности** (уровень региона):
  `CropYieldStat → YieldFeatures → YieldForecastModel → YieldForecast`
  (ridge-регрессия, LOYO-CV, доверительные интервалы CI80, внутрисезонный
  `season_progress`, история уточнений).
- **enum `YieldCrop`** уже содержит `wheat_winter` / `wheat_spring`.

## Общий принцип и ключевое ограничение

`DistrictNdviSeries.crop_type` и `Farmland.crop_type` — это **вид угодья**
(пашня / залежь / сенокос / пастбище), **а не культура**. Направления 2 и 3
требуют нового измерения — **фактической культуры на контуре**. Это центральная
новая сущность, от которой зависят остальные.

---

## Фаза 0. Подготовка данных по Тульской области (пререквизит)

Блокирует направления 2–4.

- [ ] **NDVI-покрытие**: угодья Тулы загружены (57 021 контур, `region_id=71`),
  но нужен прогон S2/L8 NDVI-пайплайна за 2–3 сезона для наполнения
  `agro_vegetation_index` → `recompute_district_ndvi_series`.
- [ ] **Эталон урожайности**: загрузить `CropYieldStat` по районам Тулы из
  регионального МСХ / ЕМИСС (источник `regional_msx` / `emiss`) — обязательно
  для обучения/валидации направлений 3–4.
- [ ] **Артефакт**: чек-лист готовности данных (без него направления 2–4 не запускаются).

## Направление 1. Мониторинг темпов уборки

**Переиспользуем:** `DistrictNdviSeries` (MODIS + S2/L8), детектор фенологии (EOS).

- [ ] Сервис `services/harvest_progress.py`: детекция события уборки как резкого
  падения NDVI после пика (спад > порога за короткое окно, поверх сглаженного
  ряда), с определением даты уборки по контуру/району.
- [ ] Агрегация: доля убранной площади по `район × культура × дата`, темп vs
  медиана прошлых лет.
- [ ] Команда `compute_harvest_progress --region "Тульская область" --year`.
- [ ] API + UI: отчёт «Темпы уборки» (вкладка в `report_*`), хороплет + прогресс-бары по районам.
- [ ] Тесты: синтетические ряды (убрано/не убрано), граничные случаи (облачность,
  повторный рост сорняков).

**Зависит от:** Фаза 0. Работает на уровне угодья/района без классификации культур
(грубо); точность растёт после направления 3.

---

## Направление 2. Разделение озимых и яровых

**Переиспользуем:** детектор фенологии `_detect_phenology` (SOS/peak),
`YieldCrop.WHEAT_WINTER/SPRING`.

- [ ] Новая модель `FarmlandCropSeason` (или поле в фенологии): признак
  озимая/яровая на `контур × год` по правилу — озимые дают ранневесенний рост
  (высокий NDVI до SOS яровых) и характерный двугорбый профиль.
- [ ] Сервис `services/winter_spring.py`: классификатор по профилю NDVI
  (ранневесенний интеграл, дата SOS, зимний baseline).
- [ ] Команда `classify_winter_spring --region --year`.
- [ ] UI: слой/отчёт «Озимые/яровые» + индикатор состояния озимых после зимы
  (контроль перезимовки — гибель озимых по низкому весеннему NDVI).
- [ ] Тесты: эталонные профили озимой пшеницы vs яровой.

**Ценность региону:** структура озимого клина, контроль перезимовки.
**Зависит от:** Фаза 0. Упрощённая (бинарная) классификация — подмножество
направления 3, реализуется раньше как быстрый результат.

---

## Направление 3. Распознавание сельхозкультур

Самое объёмное, ML-исследовательская задача.

**Переиспользуем:** `DistrictNdviSeries` / `agro_vegetation_index` (ряды по контуру),
фенологические фичи.

- [ ] Новая модель `FarmlandCropClassification`: культура на `контур × год` +
  вероятность + версия модели + источник (ML / декларация).
- [ ] Обучающая выборка: контуры с известной культурой (декларации хозяйств,
  полевые данные, VRA-карты) → размеченный датасет по Туле.
- [ ] Сервис `services/crop_classification.py`: извлечение сезонных фич NDVI по
  контуру + классификатор (RandomForest / LightGBM по временному ряду); хранение
  модели по образцу `YieldForecastModel` (коэффициенты/метрики в JSON).
- [ ] Команды `train_crop_classifier` и `classify_crops --region --year`.
- [ ] UI: карта фактической структуры посевов, сверка с отчётностью хозяйств.
- [ ] Тесты: точность на отложенной выборке, метрики per-culture.

**Зависит от:** направление 2 (озимые/яровые как фича), Фаза 0 + размеченные данные.

---

## Направление 4. Прогноз урожайности

**Что уже готово (!):** полный пайплайн `YieldFeatures → YieldForecastModel`
(ridge, LOYO-CV, CI80) → `YieldForecast` на уровне региона, с внутрисезонным
`season_progress` и историей уточнений.

- [ ] Районный scope: обучение/прогноз на уровне района Тулы (`CropYieldStat.district`,
  `YieldFeatures.district` уже поддерживают district — нужен прогон и достаточная история).
- [ ] Внутрисезонный прогноз: включить `season_complete=False` фичи fill-forward
  для оперативного прогноза до уборки (модели/поля есть, нужен планировщик пересчёта).
- [ ] Интеграция с направлением 3: прогноз по фактически распознанным культурам,
  а не по угодьям.
- [ ] UI: отчёт «Прогноз урожайности» — т/га по культурам/районам + CI, динамика
  уточнения по датам.
- [ ] Тесты: бэктест по прошлым годам Тулы.

**Зависит от:** Фаза 0 (эталон урожайности), выигрывает от направления 3.
Наименьший объём новой разработки — в основном данные + district-обучение + UI.

## Рекомендуемая последовательность

1. **Фаза 0** (данные Тулы) — блокирует всё.
2. **Направление 1** (темпы уборки) — быстрый видимый результат на существующих данных.
3. **Направление 2** (озимые/яровые) — быстрый результат, фундамент под #3.
4. **Направление 4** (district-scope + внутрисезонный прогноз) — минимум новой
   разработки, пайплайн есть.
5. **Направление 3** (распознавание культур) — самое долгое, ML + разметка;
   замыкает точность #1 и #4.
